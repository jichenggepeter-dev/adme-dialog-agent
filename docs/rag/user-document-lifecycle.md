# User-managed document collections and data lifecycle

Status: research decision for Issue #25; no runtime implementation is included.

## Plain-language goal

A user should be able to create a private collection of reference documents,
search it, understand where the files are stored, see what may be sent to a
configured model provider, and remove the collection again.

This is separate from the small FDA evidence corpus shipped with the project.
The shipped corpus is reviewed by maintainers. A user collection is untrusted
private input: the project can show where a passage came from, but it cannot
certify that the passage is correct, current, safe, or legally reusable.

## Product decisions

| Question | Decision |
| --- | --- |
| Where is a collection stored? | Under the local `data/knowledge/` runtime directory, never in the Git repository or a public Review App. |
| Does ingestion require the internet? | No. Parsing, hashing, chunking, and the first retrieval baseline are local. |
| Does a model provider receive the whole file? | No. Provider-assisted use may send the question and a small set of retrieved excerpts only after the user enables that collection for provider use. |
| Are user documents part of the repository's MIT license? | No. The uploader retains responsibility for the source material and its permissions. |
| Is PDF supported first? | No. The first implementation supports UTF-8 plain text and Markdown. PDF is a later parser-specific phase. |
| Is a vector database required? | No. The current deterministic lexical retriever remains the first baseline. |
| Can document text give the Agent new permissions? | No. Retrieved text is evidence data, never an instruction or authorization. |
| What does deletion mean? | The application removes the selected source, normalized text, chunks, and active index references. It does not promise forensic secure erasure from backups, filesystem snapshots, or SSD storage. |

## Trust boundaries

The product must keep three classes of information visibly separate:

1. **Maintainer-approved evidence** is the versioned corpus under
   `resources/evidence/`. It retains the current citation and rights review.
2. **User-provided evidence** belongs to a local collection. It is labelled
   `User-provided`, is not merged into the approved corpus, and never inherits
   an FDA or project approval label.
3. **Provider context** is the exact bounded payload allowed to leave the local
   application when a user opts into a configured model provider.

Prediction results and user documents also remain separate. A retrieved
passage may explain a concept, but it may not invent an ADME value, change an
Endpoint Registry definition, or turn a computational prediction into a
clinical or safety conclusion.

## First implementation slice

The first slice is deliberately small enough to test without introducing a
new storage service or parser stack.

### Included

- Up to 10 local collections.
- Up to 100 documents and 25 MiB of normalized text per collection.
- UTF-8 `.txt` and `.md` files, at most 2 MiB per file.
- User-visible document name, byte size, content hash, ingestion state, added
  time, optional source URL, and user-declared rights basis.
- Deterministic local lexical retrieval with source title and chunk citation.
- Create, inspect, replace, remove, and retry-failed-ingestion operations.
- A provider-context preview before the first provider-assisted use of a
  collection.

The initial limits are Research Preview safety limits, not scientific or
universal limits. They may become configurable after measurements show a real
need.

### Excluded

- PDF, DOCX, HTML, archives, images, OCR, audio, and executable content.
- URL crawling, browser import, cloud drives, and automatic synchronization.
- Remote parsing, hosted malware scanning, remote embeddings, and cloud vector
  databases.
- Multi-user access, sharing, tenant isolation, and public download links.
- Automatic scientific fact checking, paper-quality scoring, or copyright
  determination.

PDF should be a separate phase because accepting a PDF is not just adding a
filename extension. It requires a pinned parser, resource limits, malformed
file tests, encrypted-file behavior, image/OCR decisions, and a parser
vulnerability update policy.

## Storage model

The implementation should use the existing migration-managed SQLite database
for metadata and application-owned files for document content. No new database
or framework is justified for the first slice.

```text
data/knowledge/
  collections/<collection_id>/
    documents/<document_id>/
      source
      normalized.txt
    indexes/<index_version>/index.json
```

- Collection and document IDs are opaque UUIDs.
- The original user filename is metadata only. It never becomes a filesystem
  path; stored filenames are generated by the application.
- `source` and `normalized.txt` are outside the frontend's public directory.
- The directory is runtime data and must be covered by `.gitignore`, release
  secret scans, and clean-clone checks when implementation begins.
- Logs and audit records contain IDs, counts, states, and hashes, not document
  text or full local paths.

Recommended metadata:

| Record | Required fields |
| --- | --- |
| Collection | ID, display name, state, provider-access mode, created/updated time, active index version |
| Document | ID, collection ID, display name, media type, bytes, SHA-256, revision, state, rights basis, optional source URL, created/updated time |
| Index version | Version ID, schema version, source revision digest, retrieval configuration, created time, state |
| Chunk | Stable chunk ID, document ID and revision, local position, excerpt hash, lexical index data |

## Lifecycle and failure behavior

### Add

1. Check the decoded filename length, extension, actual UTF-8 readability, and
   byte limit before persistence.
2. Generate IDs and a storage path; never accept a client-supplied path.
3. Hash the bytes and normalize line endings without interpreting Markdown as
   HTML.
4. Write into a temporary document directory.
5. Build a new immutable index version, validate it, and atomically switch the
   collection's active version.
6. Expose the document as `ready` only after the new index is readable.

If ingestion fails, the active index remains usable and the failed document is
shown with a short safe error and a retry/remove action.

### Duplicate and replace

- The same SHA-256 in the same collection is a duplicate. The application
  points to the existing document instead of silently indexing it twice.
- The same display name with different bytes is not silently overwritten. The
  user chooses **Keep both** or **Replace**.
- Replace creates a new revision under the same document ID. The old revision
  remains searchable until the new index passes validation, then the active
  version changes and the old revision becomes eligible for cleanup.
- Chunk IDs include the document ID, revision, and normalized position so a
  citation never silently changes its source after replacement.

This follows the established document-store pattern of pairing a stable
document ID with a content hash and making duplicate policy explicit.

### Delete

Document and collection deletion require an explicit confirmation describing
the affected files, normalized text, chunks, and index versions.

1. Mark the target `deleting` so it cannot appear in new searches.
2. Build and validate the replacement index when deleting one document.
3. Switch the active index, then remove the target's source, normalized text,
   obsolete index files, and metadata.
4. If cleanup is interrupted, keep the item in a visible retryable deletion
   state. Startup maintenance may retry only paths derived from stored UUIDs.

Deletion is application-level removal. The UI and documentation must not claim
secure erasure: SQLite free pages, filesystem snapshots, backups, and
storage-device behavior can retain recoverable traces. A later secure-deletion
mode would need an explicit backup policy and verification; SQLite also notes
that `secure_delete` does not guarantee erasure from every virtual-table shadow
table.

### Reindex and migrate

Each index records its schema, retrieval settings, and a digest of all source
revisions. A changed chunker, tokenizer, or later embedding model creates a new
index version; it never rewrites the active index in place. A failed rebuild
leaves the last readable version active. Compatibility and rollback follow the
existing API and database migration policies.

## What may leave the local machine

Ingestion and direct local search make no provider request. A collection starts
with provider access set to `Local only`.

When the user chooses provider-assisted explanation, the interface must show:

- the configured provider and model identifier;
- the collection being used;
- that the question and retrieved excerpts may leave the machine;
- the exact excerpt text and source metadata in a provider-context preview;
- a choice to allow this request, allow future bounded excerpts from this
  collection, or cancel.

Even when allowed, the provider receives only the user's question and at most
five retrieved excerpts, with a combined excerpt budget of 6,000 characters.
It does not receive the original file, other documents, local paths, hashes,
rights notes, deleted revisions, or unrelated session and Batch data.

The activity view should record the provider, collection ID, document IDs,
chunk IDs, counts, and timestamp. It should not persist the full provider
payload in the audit log. Changing provider or broadening the transfer scope
requires a new review.

## Threat model and minimum controls

| Threat | Minimum control |
| --- | --- |
| Path traversal or filename overwrite | Generate storage paths from UUIDs; treat the displayed filename as bounded metadata. |
| Spoofed file type | Use an extension allowlist and verify that the bytes are valid UTF-8; never trust the browser `Content-Type` alone. |
| Disk or parser denial of service | Enforce request, file, collection, normalized-text, and processing-time limits before indexing. |
| HTML/script execution | Do not render raw uploaded HTML. Display Markdown-derived text through the existing safe rendering boundary. |
| Indirect prompt injection | Mark every retrieved passage as untrusted data. It cannot alter system instructions, tool permissions, confirmation requirements, or provider context limits. |
| Malicious instructions triggering tools | Retrieval and action authorization remain separate. Retrieved text cannot select a tool or approve a side effect; existing confirmation gates still apply. |
| Cross-collection leakage | Every read, search, replace, and delete query is scoped by collection ID and the current local owner boundary. |
| Data exfiltration | Default to local-only, provide exact transfer preview, cap excerpts, and never use remote parsers or scanners silently. |
| Stale or misleading sources | Preserve revision, added time, optional source URL, and user-provided label; never present the collection as maintainer-approved evidence. |
| Partial index update | Build immutable versions and switch only after validation; keep the last readable version on failure. |
| Incomplete deletion | Hide `deleting` content from retrieval and expose a retryable cleanup state rather than claiming success. |

RAG does not remove prompt-injection risk. External documents are a documented
form of indirect input, so the model must remain least-privileged and
high-impact operations must remain human-confirmed.

## Rights and privacy notice

Before adding a document, the user selects one non-legal rights note:

- `I created this material`;
- `I have permission or a license to use it`;
- `Public domain`;
- `Other authorized research use`.

The application records the user's selection but does not decide whether a use
is fair use or legally permitted. There is no fixed percentage of a work that
automatically makes a use fair. When permission is unclear, the user must
investigate the source terms or obtain permission.

User files, normalized text, and indexes are runtime data. They are not
redistributed with the repository, covered by the repository's MIT license, or
included in diagnostics and Review Apps. Exports contain citations and bounded
excerpts by default, not a copy of the complete collection.

This project remains a local, single-user Research Preview. It has no account
isolation, shared deployment, encrypted vault, backup manager, or promise of
regulatory compliance. Users should not add patient data, confidential
structures, proprietary reports, or other sensitive material unless they have
reviewed the local machine and configured provider boundary themselves.

## Proposed implementation phases

### Phase A: local text collections

- Add migration-managed collection, document, index, and chunk metadata.
- Add safe `.txt`/`.md` ingestion and application-owned local storage.
- Reuse deterministic lexical retrieval and return user-labelled citations.
- Add create, inspect, replace, delete, and reindex API contracts.
- Test limits, duplicates, path handling, failed rebuild, scoped search, and
  interrupted cleanup.

Done means a user can complete the full lifecycle without an API key and a
deleted document no longer appears in application reads or retrieval.

### Phase B: bounded provider use

- Add exact provider-context preview and per-collection opt-in.
- Keep user evidence distinct from approved evidence in structured Agent
  payloads and the frontend.
- Test provider denial, excerpt caps, cross-collection isolation, and indirect
  prompt-injection fixtures.

Done means the user can identify exactly which question and passages may leave
the machine before the first transfer.

### Phase C: PDF evaluation

- Select and pin one parser only after a parser threat review.
- Add malformed, encrypted, oversized, image-only, and resource-exhaustion
  fixtures.
- Run parsing in a bounded worker and preserve page-level citation positions.

PDF support is accepted only if it preserves the lifecycle, citation, privacy,
and failure contracts above.

### Phase D: retrieval experiments

Only after Phase A establishes a measured baseline should Issue #26 compare
keyword, vector, and metadata retrieval on the same evaluation set. A vector
store is adopted only if repeatable quality gains justify its latency,
dependencies, migration, and deletion costs.
