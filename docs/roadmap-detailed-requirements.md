## 2. 产品定义

### 2.1 一句话定位

ADME Dialog Agent 是一个本地优先、人在回路中的开源科研工作台。用户可以输入化合物，
确认软件解析出的结构，运行计算预测，查看预测字段及来源，并通过受控的对话助手完成
解释、筛选和页面操作。

### 2.2 通俗解释

ADME/ADMET 描述潜在药物如何被吸收、分布、代谢、排出，以及可能表现出的毒性。
产品展示的是计算模型生成的预测，不是实验测量，也不是医疗或安全结论。

### 2.3 目标用户

#### 主要用户

- 希望查看一个或一批候选化合物计算预测的早期药物研发研究人员；
- 不希望先自行搭建 Python、模型、API 和批处理流程的科研用户。

#### 次要用户

- 药物化学、化学信息学和相关专业学生；
- 希望研究受控 Agent、科研软件安全或前端可访问性的开源贡献者。

### 2.4 核心用户任务

```text
输入化合物
→ 确认软件解析出的结构
→ 运行单个或批量预测
→ 查看原始结果、字段说明、模型模式和来源
→ 中立地筛选或比较兼容字段
→ 导出结果
```

### 2.5 不可破坏的产品边界

- Agent 不直接生成 ADME/ADMET 数值；预测必须来自确定性预测服务。
- 名称、公共数据库编号和化学结构文本解析后都必须由用户确认。
- 未确认的结构不能进入预测。
- Mock 数据必须始终标记为测试数据，不能伪装成真实模型结果。
- Agent 不得推荐最佳候选、生成综合分数或作临床、监管、安全结论。
- 未验证的单位、概率含义、正类、方向性和数据来源必须保持未知。
- Agent 只能使用白名单工具和白名单页面动作。
- Agent 不得执行任意 Shell、代码、文件操作、网页访问或注册表修改。
- 会话、资源、确认记录和页面动作必须保持会话隔离。
- 默认不收集遥测，不默认上传完整数据集。

## 3. 路线图优先级

| 优先级 | 含义 |
| --- | --- |
| Must | 版本不能缺少；不通过则版本不发布 |
| Should | 高价值但可在时间不足时降级，不阻止最小版本 |
| Could | 探索或体验增强，仅在 Must 全部通过后实施 |
| Post-deadline | 明确不进入 2026-08-10 课程交付 |

## 4. 所有功能共同的完成定义

每个功能只有同时满足以下条件才算完成：

1. 需求、范围和非目标已经写清楚；
2. API 和前端数据结构有严格类型或 Schema；
3. 正常、空状态、失败、超时和权限拒绝路径有明确行为；
4. 涉及 Agent 的功能有安全、会话隔离和越权测试；
5. 涉及科研描述的功能有 Mock/Real、未知元数据和禁止结论测试；
6. 后端相关测试通过；
7. 前端相关 lint、typecheck、unit test 和 build 通过；
8. 核心用户流程有 E2E 或可重复的人工验收步骤；
9. 用户文档、配置示例和限制说明同步更新；
10. 没有提交凭据、运行数据库、上传文件、缓存或用户数据；
11. 验收报告明确区分 Mock 验证、真实模型验证和未验证事项。

通用工程门禁：

```bash
make test
cd frontend
npm run lint
npm run typecheck
npm run test
npm run build
```

改变核心用户流程时还必须运行相关 Playwright E2E。真实 ADMET-AI 检查是单独的集成
验证；只有真实模型实际运行成功时，才能报告真实模型通过。

# 5. 2026-08-10 课程交付：v0.1 Research Preview

## 5.1 版本目标

让另一位不熟悉本项目的人能够：

1. 理解项目解决什么问题和不解决什么问题；
2. 从公共仓库安全地安装和启动；
3. 在没有 API Key 和真实模型的情况下运行可重复测试；
4. 看懂核心工作流和 Agent 权限边界；
5. 提交 Issue 或贡献修改；
6. 看到两个新的端到端能力：流式 Assistant 和带引用的证据检索。

## 5.2 当前状态

已经完成：

- 产品定位、非目标和科研责任边界；
- 开源许可证、贡献指南、行为准则、安全政策和第三方说明；
- 可发布文件中的 secrets 和运行数据清理；
- Single、Batch、About 三个主要页面；
- 跨页面 Assistant、严格工具、确认机制、会话状态和 UI Action；
- Endpoint Registry 的 104 个字段说明框架；
- 本地 Mock 测试、前端测试和构建；
- 已公开的 CI、安全更新和依赖兼容提交；
- 第二个全新环境的 clean-clone 安装、测试和 Mock 浏览器验证；
- 当前文档索引、权威资料与历史实现记录分类；
- 发布前 secrets、依赖许可证、模型/数据集风险和素材权利复查。

尚未完成：

- 实现流式 Assistant；
- 实现小型 RAG 证据检索；
- 准备课程演示与最终进度证据。

## 5.3 R01：公开发布剩余 hardening 提交

优先级：Must

### 用户需求

作为贡献者，我希望公共仓库包含已经通过本地验证的依赖、安全、兼容性和 CI 修改，
这样我下载到的代码与项目声称的状态一致。

### 具体范围

- 复核本地提交与远端基线的父子关系；
- 按小而可审查的提交顺序发布；
- 禁止强推、重写历史或把多个提交压成一个无法审查的提交；
- 每次发布后核对远端 SHA；
- 最终确认 GitHub Actions 对公开提交运行。

### 非目标

- 不在这个任务中顺便重构代码；
- 不修改历史提交日期来制造开发时间线；
- 不创建部署、生产配置或线上服务。

### 验收标准

- 远端 `main` 精确指向预期的最终提交；
- 所有发布都是普通 fast-forward；
- 本地和远端提交历史一致；
- GitHub Actions 已触发，结果和链接被记录；
- 如 CI 失败，报告真实失败，不将本地通过等同于远端通过；
- 工作树没有被发布过程意外修改。

## 5.4 R02：Clean-clone 可复现安装

优先级：Must

### 用户需求

作为第一次接触项目的贡献者，我希望只按照公共 README 就能安装、运行 Mock 模式并
执行测试，而不依赖作者机器上的隐藏文件或已有环境。

### 具体范围

- 在第二个全新目录或隔离环境 clone 公共仓库；
- 使用项目声明的最低支持版本之一完成安装；
- 不复制作者现有 `.venv`、`node_modules`、数据库或 `.env`；
- 从 `.env.example` 开始配置；
- 运行 Mock 开发模式和通用工程门禁；
- 记录实际命令、耗时、平台、版本和失败修正。

### 验收标准

- 新环境中不存在来自原工作区的未跟踪依赖或运行数据；
- `make setup` 或文档规定的等价流程成功；
- `ADME_MOCK_MODE=true make dev` 能启动前后端；
- `/single`、`/batch` 和 `/about` 可以打开；
- 通用工程门禁全部通过；
- 至少执行一个 Single Mock 用户流程；
- README 中的命令与实际操作一致；
- 所有必须的手动步骤都写入文档；
- 验收报告不把 Mock 结果称为真实 ADMET-AI 验证。

## 5.5 R03：文档信息架构与历史归档

优先级：Must

### 用户需求

作为用户或贡献者，我希望快速知道哪些文档是当前有效说明、哪些只是实现历史，从而
避免按照已经过期的计划或接口工作。

### 具体范围

- 建立当前文档入口和分类；
- 将产品、安装、测试、Agent、安全、API 和科研元数据文档列为权威资料；
- 将旧计划、阶段交接和审查报告明确标记为历史记录；
- 修复失效链接和相互矛盾的状态描述；
- 明确 `ROADMAP.md` 是公开简版，本文是内部详细规划。

### 验收标准

- `docs/README.md` 能把读者引导到当前权威文档；
- 历史记录不会被描述成当前未完成任务；
- README、ROADMAP、测试指南和 Agent 文档没有关键矛盾；
- 所有仓库内 Markdown 相对链接通过检查或人工抽查；
- 新贡献者能在五分钟内找到安装、测试、安全边界和贡献方式；
- 不删除仍有审计价值的历史记录。

## 5.6 R04：发布前安全、许可证与素材审查

优先级：Must

### 用户需求

作为维护者和使用者，我希望仓库不包含凭据、私人运行数据或权利不明的素材，并清楚
知道第三方代码、模型、数据和媒体的许可边界。

### 具体范围

- 扫描当前文件和 Git 历史中的常见 secret 模式；
- 检查 `.env`、密钥、Token、Cookie、数据库、上传内容和本地日志；
- 审查 Python、npm、ADMET-AI、模型、数据集和图片许可；
- 核对第三方说明和素材来源；
- 将无法确认的项目记录为发布风险。

### 验收标准

- 当前提交中不存在真实凭据或用户运行数据；
- `.gitignore` 覆盖本地凭据、数据库、上传、缓存和构建产物；
- 许可证和第三方说明与实际依赖一致；
- 每张公开截图或媒体都能说明来源或作者权利；
- 未确认的模型或数据再分发权利被明确披露，不作错误授权承诺；
- 审查命令、日期、结果和剩余风险被保存。

## 5.7 R05：CI 与发布证据

优先级：Must

### 用户需求

作为贡献者，我希望每次 push 和 PR 都自动验证 Mock 后端与前端基础质量，而不需要
任何私密 API Key。

### 具体范围

- GitHub Actions 后端测试；
- 前端 lint、typecheck、unit test 和 production build；
- 最小只读权限；
- 禁用不需要的遥测和 hosted tracing；
- 使用临时数据库；
- 缓存依赖但不缓存用户数据；
- 设置合理超时和并发取消。

### 验收标准

- 新提交和 PR 能自动触发 CI；
- CI 不需要任何项目 secret；
- 后端使用 `ADME_MOCK_MODE=true` 且 Agent provider 默认关闭；
- 前端使用锁文件和 `npm ci`；
- 后端和前端 Job 的成功或失败状态清晰可见；
- 失败日志不会输出凭据、完整 prompt、用户文件或完整 Batch 数据；
- 本地门禁和 CI 门禁没有关键缺口；
- 真实模型未在 CI 中运行时，文档明确说明 CI 只验证 Mock 工程路径。

## 5.8 R06：流式 Assistant 响应

优先级：Must

### 用户需求

作为使用 Assistant 的用户，我希望在模型和工具工作过程中看到持续进度，而不是长时间
等待一个没有反馈的界面；同时我需要明确区分“正在生成文字”“调用工具”“等待我确认”
和“已经完成”。

### 功能拆分

#### R06.1 后端流式协议

- 为聊天提供明确版本化的流式端点或响应模式；
- 定义允许的事件类型：
  - `message_delta`
  - `tool_started`
  - `tool_completed`
  - `confirmation_required`
  - `response_completed`
  - `error`
  - 可选 `heartbeat`
- 每个事件包含 session、message、correlation 和顺序标识；
- 事件 payload 使用严格 Pydantic Schema；
- 流结束必须有唯一终态。

#### R06.2 前端增量渲染

- 在同一条 Assistant 消息中追加文本；
- 工具活动和确认卡不混入普通正文；
- 明确显示连接中、工具运行、等待确认、完成、失败；
- 页面切换后仍保持同一会话；
- 避免重复消息、重复卡片和重复 UI Action。

#### R06.3 确认、安全与恢复

- 流式传输不能绕过结构确认或副作用确认；
- 中断时不自动重复执行工具或确认；
- 用户可重新发起安全的文本请求；
- 对已发生但响应丢失的确认操作，先查询权威状态；
- 超时、断网和 provider 错误返回稳定错误，而不是内部异常。

#### R06.4 兼容性

- 保留现有非流式接口，或提供明确迁移期；
- Mock provider 能生成确定性的流式事件用于测试；
- 不要求真实 provider 才能完成核心自动测试。

### 非目标

- 不显示模型思维链；
- 不把 token 级速度作为科研正确性的证明；
- 不在流式协议中传输完整 Batch 数据或任意内部工具参数；
- 不增加 Agent 的工具权限；
- 不自动重试可能产生副作用的请求。

### 验收标准

- 首个可见事件在 Mock 测试环境中能稳定出现，不需要等待完整回答；
- 文本增量按顺序组合成最终消息，无丢字、乱序或重复；
- 工具开始和结束状态与真实工具调用一致；
- `confirmation_required` 到达后预测不会提前运行；
- 每个请求只有一个 `response_completed` 或终止 `error`；
- 刷新或跨页面切换不会导致同一工具重复执行；
- 断流、超时和取消都有可理解的恢复提示；
- 未知事件类型被安全拒绝或忽略并记录，不执行动作；
- 会话 A 的事件不能出现在会话 B；
- Mock/Real 标签在流式结果中保持正确；
- 后端协议测试、前端 reducer/renderer 测试和至少一个流式 E2E 通过；
- 非流式回归测试继续通过。

## 5.9 R07：ADME Evidence RAG 最小闭环

优先级：Must

### 用户需求

作为不熟悉某个预测字段的用户，我希望 Assistant 先从允许使用的可靠资料中查找证据，
再解释字段含义和限制，并清楚告诉我答案来自哪里；如果没有证据，它应该承认不知道。

RAG（检索增强生成）在这里指：回答之前先检索相关文档片段，再让模型基于这些片段组织
答案。它不是让模型自行访问整个互联网，也不是让 RAG 替代预测模型。

### 功能拆分

#### R07.1 来源政策与小型语料库

- 选择 5–10 个允许使用、来源稳定且与项目范围相关的资料；
- 优先使用官方文档、原始论文、公开数据说明和项目已有来源；
- 为每个来源记录：
  - 标题
  - 作者或机构
  - 稳定链接
  - 版本或访问日期
  - 许可或使用依据
  - 覆盖主题
- 第一版只覆盖吸收、分布、代谢、清除和毒性中的有限问题。

#### R07.2 文档处理与索引

- 文档提取失败时显式报告；
- 文本切片保留来源、页码或章节和稳定片段 ID；
- 索引过程可重复，不依赖未提交的作者本地文件；
- 支持删除并重建索引；
- 不把用户完整私有文档默认发送给外部 provider。

#### R07.3 检索

- 根据问题返回有限数量的相关片段；
- 每个片段带来源和位置；
- 对同一输入和固定索引提供可复现的测试结果；
- 检索与回答分开记录，便于判断错误发生在检索还是生成。

#### R07.4 有引用的回答

- 回答只对检索到的证据作有限总结；
- 页面展示来源标题、稳定链接、页级或章节级证据和验证状态；
- 预测数值仍来自预测服务，不从文献中编造；
- Endpoint Registry 与外部文献冲突时，显示冲突而不是自动覆盖；
- 用户能区分：
  - 模型预测
  - Registry 元数据
  - 文献证据
  - Assistant 总结

#### R07.5 证据不足与拒答

- 检索不到相关来源时明确说证据不足；
- 来源只支持部分结论时限定回答范围；
- 不用模型常识补全缺失单位、阈值、概率或临床含义；
- 医疗、患者、剂量或候选推荐问题继续按现有 Guardrail 拒绝。

#### R07.6 评测

- 建立 10–15 个可人工判断的问题；
- 至少覆盖：
  - 能正确回答并引用；
  - 需要组合两个片段；
  - 元数据未知；
  - 来源互相冲突；
  - 检索不到；
  - 临床或推荐越界；
  - Mock/Real 混淆诱导；
- 保存预期来源、允许结论和禁止结论。

### 非目标

- 不支持任意用户 PDF 上传；
- 不自动大规模抓取论文数据库；
- 不构建 GraphRAG；
- 不替代 Endpoint Registry；
- 不输出临床建议、候选排序或“安全/不安全”结论；
- 不承诺覆盖全部 104 个输出字段；
- 不把引用数量当作回答正确性的充分证明。

### 验收标准

- 语料库包含 5–10 个有来源和使用依据的文档；
- 每个索引片段能追溯到原文位置；
- 索引可从仓库说明在新环境重建；
- 至少 10 个评测问题可重复运行；
- 引用精确度、检索命中和拒答结果被分别记录；
- 回答中的关键事实能由显示的证据支持；
- 不存在引用与正文无关、链接错误或页码丢失；
- 证据不足问题 100% 返回明确的不足说明；
- 临床、候选排名和无依据安全结论为 0；
- 不编造单位、正类、概率、阈值或模型置信度；
- 用户能看出哪部分是预测、哪部分是文献；
- RAG 关闭或索引不可用时，原有预测和 Agent 工作流仍可使用；
- 依赖和许可证审查通过；
- 后端检索测试、回答 Guardrail 测试、前端来源卡测试和至少一个 RAG E2E 通过。

## 5.10 R08：产品设计审查

优先级：Should

### 用户需求

作为第一次使用产品的人，我希望理解当前状态、下一步操作和 Assistant 的权限，不需要先
学习所有化学或 Agent 术语。

### 具体范围

- 审查 Single、Batch、About 和 Assistant 的完整任务路径；
- 检查信息层级、术语解释、空状态、错误恢复、键盘路径和移动端；
- 检查结构确认、Mock 警告、来源卡和流式状态是否容易区分；
- 形成问题列表并按严重度、用户影响和修复成本排序。

### 验收标准

- 至少覆盖新用户首次使用、Single、Batch、About、流式和 RAG；
- 每个问题包含证据、受影响步骤、严重度和建议；
- 不以纯视觉偏好代替用户任务和可访问性判断；
- Must 级问题在发布前修复或明确阻塞发布；
- 审查结果保存到仓库。

## 5.11 R09：Agent Activity & Evidence Trace

优先级：Could

### 用户需求

作为科研用户，我希望知道 Assistant 做了什么、使用了哪些工具和来源、等待我批准什么，
以及失败后如何恢复。

### 具体范围

- 展示经过脱敏的时间线：
  - 用户请求
  - 工具开始/结束
  - 用户确认
  - 来源引用
  - 未知或证据不足
  - 错误和恢复动作
- 默认展示用户可理解的活动，不显示内部 prompt 或原始工具参数；
- 与本地 audit 记录使用稳定 correlation ID 对齐。

### 非目标

- 不展示思维链；
- 不显示 API Key、Authorization、完整 prompt、完整 Batch 或原始 provider 响应；
- 不允许用户从面板执行任意工具。

### 验收标准

- 时间线顺序与实际操作一致；
- 每个活动有清楚状态和时间；
- 敏感字段在前后端都不会进入展示 payload；
- 来源卡能从活动记录返回对应证据；
- 错误活动包含可执行的恢复建议；
- 键盘和屏幕阅读器可以访问；
- 不影响核心 Assistant 响应性能和会话隔离。

## 5.12 R10：课程现场演示与备份

优先级：Must

### 用户需求

作为教授，我希望在不了解药物研发细节的情况下，看懂产品解决的问题、已经完成的 FOSS
工作、当前限制和下一步计划。

### 演示流程

1. 用通俗语言解释产品和 ADME/ADMET；
2. 输入一个已知化合物；
3. 展示结构确认；
4. 运行 Mock 或真实预测，并明确说明模式；
5. 查看字段说明和来源；
6. 使用 Assistant 完成一个受控动作；
7. 展示流式状态；
8. 提出一个能被来源支持的问题；
9. 提出一个证据不足或越界问题并展示拒答；
10. 展示 GitHub FOSS 文档、CI 和贡献入口。

### 验收标准

- 主演示在预定时间内完成；
- 每一步有预期结果和失败备选；
- 外部服务不可用时可使用明确标记的 Mock 和截图；
- 备份截图与当前版本一致；
- 演示不声称 Mock 是真实科学验证；
- 能清楚回答“这个项目的 FOSS 工作是什么”；
- 能清楚说明未完成任务和截止后范围。

# 6. v0.2：Trust and Control

## 6.1 版本目标

用户可以运行、理解、评估、导出和删除 Agent 状态，而不需要放弃数据控制。

## 6.2 T01：确定性 Mock Agent Provider

优先级：Must

### 需求

没有模型 API Key 的贡献者也能完整演示 Agent 工具、确认、错误和恢复流程。

### 验收标准

- 不需要外部 provider 或 API Key；
- 相同输入产生稳定、版本化的事件和工具路径；
- 可构造成功、确认、超时、工具失败和证据不足场景；
- Mock provider 不生成真实科研结论；
- UI 始终标记 Mock；
- CI 能运行核心 Agent E2E。

## 6.3 T02：会话与对话导出

优先级：Must

### 需求

用户可以查看并带走自己的对话、确认记录和有限活动历史。

### 具体范围

- 导出格式使用版本化 JSON，另可提供易读 Markdown；
- 明确包含和排除的字段；
- 导出前需要确认；
- 默认不包含 API Key、内部 prompt、完整 audit payload 或不必要的 Batch 数据。

### 验收标准

- 只能导出当前会话拥有的数据；
- 跨会话资源访问被拒绝；
- 导出文件能通过 Schema 验证；
- 导出时间、版本和模式明确；
- 敏感字段扫描为零；
- 大会话有大小限制和可理解错误；
- 导出动作有审计记录。

## 6.4 T03：会话与本地数据删除

优先级：Must

### 需求

用户可以明确删除会话及其关联资源，并知道哪些数据被删除、哪些因技术或审计原因保留。

### 具体范围

- 删除必须二次确认；
- 删除会话、消息、业务状态、确认、资源和允许删除的 audit 引用；
- 定义 Batch 文件、上传文件和共享资源的处理规则；
- 支持幂等删除；
- 不依赖仅在前端隐藏。

### 验收标准

- 未确认删除不会改变数据；
- 删除只能作用于当前会话；
- 删除成功后资源 API 返回稳定的不存在状态；
- 重复删除不会恢复或破坏其他数据；
- 失败时不出现半删除或有恢复策略；
- 页面清除本地 session ID；
- 删除行为有最小且脱敏的安全记录；
- 相关数据库和 E2E 测试通过。

## 6.5 T04：可复现 Agent 评测集与运行器

优先级：Must

### 需求

维护者能够用固定案例判断一次修改是否破坏工具选择、确认、安全或多轮上下文。

### 验收标准

- 评测案例使用版本化、可审查格式；
- 每个案例包含输入、预期工具、禁止工具、确认要求和禁止表达；
- 支持只运行某类案例；
- 输出机器可读和人可读报告；
- 报告区分确定性规则、Mock provider 和真实 provider；
- 不把少量评测题称为通用科学正确性证明；
- CI 至少运行确定性评测子集。

## 6.6 T05：确认、安全语言和 Provider 失败评测

优先级：Must

### 验收标准

- 必须确认的动作合规率为 100%；
- 未确认预测执行数为 0；
- 跨会话资源泄漏为 0；
- 禁止临床、监管、安全和候选排名结论为 0；
- 未知元数据过度解释为 0；
- Mock 伪装为真实结果为 0；
- Provider 超时、限流、断连和无效响应都有稳定用户反馈；
- 失败不会自动重复执行副作用工具。

## 6.7 T06：自动化无障碍检查

优先级：Should

### 具体范围

- 将自动化无障碍检查加入核心页面；
- 保留键盘和屏幕阅读器人工检查；
- 覆盖动态流式内容、确认卡、来源卡和错误状态。

### 验收标准

- 核心页面没有已知严重自动化违规；
- 所有交互控件可键盘访问；
- 焦点顺序与视觉顺序一致；
- 动态状态通过适当 live region 提示且不过度打扰；
- 颜色不是唯一状态表达；
- 自动化结果不被描述成完整无障碍认证。

## 6.8 T07：隐私和安全回归覆盖

优先级：Must

### 验收标准

- 测试覆盖跨会话访问、确认重放、过期状态、重复 action、资源越权；
- audit、日志和错误响应不会出现凭据或完整敏感 payload；
- 上传和 Batch 数据不会无条件进入模型上下文；
- Provider 只接收文档声明的最小上下文；
- 禁用 hosted tracing 的配置有回归测试；
- 依赖漏洞和高风险变更有明确响应流程。

# 7. v0.3：Contributor Experience

## 7.3 C02：Onboarding 与示例工作流

优先级：Must

### 具体范围

- 15 分钟 Quick Start；

- API 变更规则和废弃流程明确；
- 破坏性变更提供迁移说明；
- 文档示例通过合同测试或自动验证。

## 7.5 C04：数据库 Schema 迁移工具

优先级：Must

### 需求

升级应用时，用户本地会话和资源不能依赖手工编辑 SQLite。

### 验收标准

- Schema 有独立版本号；
- 迁移按顺序、事务化执行；
- 已迁移数据库不会重复迁移；
- 旧版本 fixture 可升级；
- 不支持的降级有明确错误；
- 迁移前备份或恢复说明明确；
- 失败不会留下被错误标记为成功的版本。

## 7.6 C05：一条命令完成贡献者验证

优先级：Must

### 验收标准

- 一条文档化命令运行格式、静态检查、后端测试、前端测试和 build；
- 可选 E2E 和真实模型检查与默认快速门禁分开；
- 失败返回非零退出码；
- 输出指出失败层级和下一步；
- 本地命令与 CI 关键步骤一致；
- 不需要 provider secret 完成默认门禁。

## 7.7 C06：第一次结构化外部可用性研究

优先级：Should

### 具体范围

- 招募至少 3–5 名符合主要或次要用户定义的参与者；
- 使用固定任务观察，不引导具体点击；
- 收集任务完成、耗时、错误、术语困惑和信任问题；
- 不把参与者反馈用作科学验证。

### 验收标准

- 研究问题、参与者标准、任务脚本和同意方式明确；
- 记录不包含不必要的个人或科研敏感数据；
- 结果区分观察事实、用户意见和产品推断；
- 形成按影响排序的改进项；
- 至少一个高频问题进入后续 roadmap。

# 9. 截止后研究方向

以下方向可以研究，但在形成可验证用户价值和安全方案前，不承诺进入具体版本。

## 9.1 P01：用户管理的文档集合

研究问题：

- 用户如何添加、查看、更新和删除自己的资料？
- 文档存储在哪里，是否发送给外部 provider？
- 如何处理版权、隐私、重复文件和索引版本？

进入实现前的门槛：

- 数据生命周期和删除语义明确；
- 文件类型、大小和数量边界明确；
- 威胁模型、解析失败和恶意文档处理方案明确；
- 用户能看见哪些数据离开本机。

## 9.2 P02：Hybrid Retrieval

研究关键词检索、向量检索和元数据过滤的组合，目标是提高有限语料库中的可解释检索。

进入实现前的门槛：

- 现有 RAG 评测已形成稳定基线；
- 新方法在相同评测集上有可重复提升；
- 延迟、依赖和维护复杂度可以接受；
- 提升不是来自泄漏答案或扩大不受控语料。

## 9.3 P03：Knowledge Graph / GraphRAG

潜在实体：

- 化合物
- 预测字段
- 数据集
- 论文
- 测量单位
- 来源和版本

进入实现前的门槛：

- 有明确用户任务无法由简单 RAG 完成；
- 图 Schema、实体解析和来源更新策略明确；
- 图关系有证据，不由模型自由编造；
- 与现有 Registry 的权威关系明确；
- 有专门评测证明收益大于复杂度。

## 9.4 P04：受限 Loop / Graph Orchestration

可能场景：

- 检索后发现证据不足，执行一次有限的查询改写；
- 对多个独立来源并行检索后汇总；
- 工具失败后按允许策略恢复。

进入实现前的门槛：

- 每个循环有最大次数、预算、超时和终止条件；
- 每一步工具和数据权限明确；
- 重复调用、死循环和副作用重放有测试；
- 单 Agent 线性流程确实无法满足任务；
- 活动记录能让用户理解发生了什么。

## 9.5 P05：Multi-Agent

当前没有成立的产品需求。只有出现可证明的独立角色、并行任务或权限分离需求时才重新
评估。不能仅因为 Multi-Agent 是热门架构而引入。

进入实现前的门槛：

- 每个 Agent 有互不重复的职责和权限；
- 单 Agent 基线已经达到上限；
- Agent 间信息丢失、重复工具和责任归属可评测；
- 延迟、成本和调试复杂度有可接受收益。

# 10. 明确不规划

- 自动候选药物排名或推荐；
- 临床、医疗、患者、剂量、监管或最终安全决策；
- 将预测值自动翻译为“更好”“更安全”或“可以使用”；
- 通用科研 Agent 框架或插件市场；
- 托管式多用户 SaaS；
- 默认遥测、云同步或完整数据集上传；
- Agent 任意 Shell、代码、文件、浏览器或外部网络权限；
- 未经验证自动修改 Endpoint Registry；
- 未经用户明确授权的生产部署或真实用户数据操作。

# 11. 指标体系

## 11.1 北极星指标

核心探索任务成功率：

> 用户能够确认结构、运行预测、理解模式和来源，并在不产生无依据科学结论的前提下
> 查看、比较或导出结果。

## 11.2 过程指标

- 首次成功启动率；
- 从输入到可见结果的任务完成率和耗时；
- 结构确认完成率；
- 错误恢复成功率；
- RAG 来源卡打开率和证据查看率；
- 新贡献者完成 Quick Start 的时间；
- PR 首次通过门禁比例。

## 11.3 Agent 和 RAG 质量指标

- Tool selection accuracy；
- Tool argument accuracy；
- 多轮指代解析正确率；
- 检索命中率；
- 引用精确度；
- 有证据回答率；
- 证据不足拒答准确率；
- Provider 失败恢复率。

## 11.4 硬性 Guardrail 指标

- 未确认高影响动作：0；
- 跨会话数据泄漏：0；
- Mock 被描述为真实结果：0；
- 编造单位、概率、置信度、阈值或来源：0；
- 临床、安全、监管或候选排名结论：0；
- 仓库中的真实 secrets 或用户运行数据：0。

GitHub stars、下载量和对话次数只能作为发现与使用信号，不能证明科研价值或产品成功。

# 12. 建议的近期执行顺序

严格按以下顺序推进：

1. **冻结 v0.1 范围**：不再加入本文未列入 Must 的截止前功能；

6. **RAG 最小闭环**：先定来源和评测题，再选实现；

8. **完整门禁和相关 E2E**；
9. **课程演示、截图和最终报告**；
